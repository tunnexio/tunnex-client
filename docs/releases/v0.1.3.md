# Tunnex Desktop v0.1.3

Status: prepared release notes; not published. No installer availability or
installed-build acceptance is implied until the release checklist is complete.

## Changes

- Managed enrollment now lives in the standalone client repository, including
  the Electron shell, renderer, IPC bridge and regression coverage (PR #4).
- Organization selection for managed enrollment, with an explicit lock to the
  enrolled organization and clearer remove-device/re-enrollment guidance.
- Durable enrollment state and serialized lifecycle operations to guard against
  stale credentials, conflicting account changes and interrupted enrollment.
- Retains the larger macOS tray branding and scoped-DNS permissions fixes from
  earlier client changes.

## Compatibility and limitations

The new S20.5 enrollment path requires a compatible Tunnex control plane. Its
companion server work is tracked in
[tunnex PR #56](https://github.com/tunnexio/tunnex/pull/56). Do not advertise
universal compatibility with older CP releases or claim the companion changes
are released merely because this client package exists.

Windows automatic terminal crash recovery remains deferred to S20.5.1. No new
helper recovery protocol is included. This release preparation does not expand
the AWS Kubernetes walk's provider or lifecycle qualification.

Current packaging is not macOS Developer ID signed/notarized. Windows signing
depends on the configured signing service; record the actual artifact result,
not an assumed signed status. No auto-update feed is configured: distribute
verified installers through the release page and normal organizational policy.

## Release checklist

1. Merge the version preparation PR only after its exact-head platform checks
   pass; record the resulting main commit as the release source.
2. Verify root and `apps/client/package.json` both contain `0.1.3`, the source
   includes merged PR #4, and no `v0.1.3` tag/release already exists.
3. Obtain publication authorization, then create `v0.1.3` at that exact verified
   source. Pushing the tag triggers the existing build-and-publish workflow;
   it is not a draft-only operation. Never move or overwrite an existing tag.
4. Verify helper tests/cross-compilation and both native platform packaging
   jobs succeed. Tagged Windows builds must include Wintun; do not weaken the
   existing missing-DLL release guard.
5. Verify the release contains all three non-empty assets:
   `Tunnex-macOS-universal.pkg`, `Tunnex-Windows-x64.exe`, and `SHA256SUMS`.
   Independently verify downloaded installers against the checksum file and
   inspect their embedded version and actual signing status.
6. Smoke-test the packaged builds against the intended compatible CP: existing
   profile preservation, sign-in/enrollment, organization selection, connection,
   private VIP/FQDN access, disconnect and removal/re-enrollment. Keep credentials
   out of logs and evidence. Unrun platform checks remain explicitly unqualified.
7. Replace these prepared notes with verified publication details and link the
   assets. Do not treat creation of a release page as successful distribution.

The previous `v0.1.2` release page had no attached assets when checked on
2026-09-06. Workflow run `33974043640` failed publication because tag `0.1.2`
did not match package version `0.1.1`. Both manifests in this preparation are
`0.1.3`; the existing mismatch guard is preserved. This does not alter the older
release or move its tag.

Preparation checks: frozen install, client typecheck/build and all 293 client
tests passed. Native installer builds are delegated to the release-preparation
PR's platform CI; this local result is not packaged-build or live-install proof.

Local and hosted source checks for the managed-enrollment transfer are recorded
in `docs/S20.5-client-extraction-decisions.md`. Its broader renderer fixture and
root typecheck limitations remain distinct from the passing direct client and
